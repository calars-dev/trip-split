# 여행 타임라인 — 설계

**작성일** 2026-07-27
**대상** trip-split (여행 정산 웹앱)

지출 목록이 "입력한 순서"로만 쌓여서, 여행이 끝나고 보면 어떤 흐름으로 놀았는지가
안 보인다. 그리고 그 자리에서 못 적고 나중에 몰아 적으면 "이게 언제 쓴 돈이었지"가
헷갈린다. 이 두 가지를 푼다.

## 만드는 것 3개

1. **일차 · 시간대 지정** — 지출마다 "3일차 저녁"을 붙일 수 있다. 여행 시작 전에
   산 것(항공권·숙소·준비물)은 "여행 전 준비" 칸으로 간다.
2. **타임라인 뷰** — 기존 `내역` 화면을 일차별 타임라인으로 교체한다. 하루 안에서
   아침→점심→오후→저녁→밤 순으로 흐르고, 일차마다 그날 쓴 총액과 막대가 붙는다.
3. **멤버별 필터** — 이름을 탭하면 그 사람 기록만 본다. `낸 것`(결제자)과
   `나눈 것`(부담액) 두 탭.

## 데이터

### `rooms` — 칸 1개 추가

| 칸 | 타입 | 뜻 |
|---|---|---|
| `start_date` | `date` | 여행 시작일 = 1일차 |

DB에서는 null을 허용한다. 이미 만들어진 방들이 있어서 `not null`로 걸면 그 방들이
깨진다. **새 방을 만들 때만 화면에서 필수**로 받는다.

### `expenses` — 칸 3개 추가

| 칸 | 타입 | 뜻 |
|---|---|---|
| `day_index` | `smallint` | 0 = 여행 전 준비, 1 = 1일차, 2 = 2일차 … |
| `slot` | `text` | `'아침'` `'점심'` `'오후'` `'저녁'` `'밤'` |
| `seq` | `int` | 같은 (일차, 시간대) 안에서의 순서 (0부터) |

시간대는 기존 카테고리(`'식비'`, `'카페'` …)처럼 한글 키를 그대로 쓴다. 코드에 이미
그 방식이 깔려 있다.

**달력 날짜는 지출에 저장하지 않는다.** 화면에 띄울 때만 `start_date + (day_index-1)`로
계산한다. 이유는 사용자가 생각하는 단위("3일차 저녁")와 저장 단위를 1:1로 맞추기
위해서다. 부수 효과로 "여행 전 준비"가 `day_index = 0`으로 자연스럽게 표현된다.
실제 입력 시각은 `created_at`에 그대로 남아 있으므로 추적은 가능하다.

### 시작일이 바뀌면 일차가 따라 움직인다 (2026-07-28 개정)

**1일차는 언제나 시작일이다.** 시작일을 고치면 지출은 *실제로 있었던 달력 날짜에
그대로 머물고*, 대신 일차 번호가 통째로 이동한다. 새 시작일보다 이른 것은 `0`(준비)로
내려가고 시간대를 잃는다.

처음 설계는 반대였다 — "시작일을 고쳐도 일차는 안 흔들린다(달력 날짜만 바뀐다)".
그게 틀렸다는 게 실제 데이터에서 드러났다. 교토 여행 방의 마이그레이션 결과가
`1일차 1건 / 2·3일차 없음 / 4일차부터 재개`로 나왔는데, 원인은 출발 3일 전에 결제한
숙소 선결제가 "가장 이른 지출"로 잡혀 시작일이 3일 앞당겨진 것이었다. 사용자가 앱에서
시작일만 고쳤다면 달력 라벨만 바뀌고 **일차는 여전히 3씩 밀린 채**였을 것이다.
고칠 방법이 앱 안에 없었다.

구현 주의점:

- **쓰는 방향에 순서가 있다.** 일차를 당길 땐(`delta > 0`) 낮은 일차부터, 밀 땐 높은
  일차부터 갱신한다. 반대로 하면 아직 읽어야 할 일차에 덮어쓴다.
- **여러 날이 한꺼번에 준비로 모이면 `seq`가 충돌한다.** 이동이 끝난 뒤 준비 묶음을
  `created_at` 순으로 다시 0,1,2…로 매긴다.
- **준비(0)에 있던 것은 시작일을 앞당겨도 준비에 남는다.** 달력 날짜를 저장하지 않아
  되돌릴 근거가 없기 때문이다. 되돌리려면 사람이 그 지출의 일차를 직접 고른다.

### 인덱스

```sql
create index if not exists idx_expenses_timeline
  on public.expenses(room_id, day_index, seq);
```

## 마이그레이션 (`migration-timeline.sql`)

한 번만 실행하고, **여러 번 실행해도 안전**해야 한다(빈 칸만 채운다).

1. **칸 추가** — `add column if not exists`.
2. **`start_date` 채우기** — 방마다 가장 이른 지출 날짜(한국시간). 지출이 하나도
   없는 방은 방 생성일로.
3. **`day_index` · `slot` 채우기** — `created_at`을 **`Asia/Seoul`로 변환한 뒤**
   날짜에서 일차를, 시(hour)에서 시간대를 뽑는다. 시작일보다 이르면 `0`(준비).
4. **`seq` 채우기** — `(room_id, day_index, slot)`으로 묶어 `created_at` 순서대로
   0,1,2… 부여.

시간대 판정:

```
05–09시 → 아침    10–13시 → 점심    14–16시 → 오후
17–20시 → 저녁    21–04시 → 밤
```

> ⚠️ **한국시간 변환이 핵심이다.** Supabase는 UTC로 저장하므로 변환을 빼면 밤 9시
> 이후 지출이 전부 다음날로 밀려 일차가 하루씩 어긋난다.

`seq`는 `not null default`를 주지 않고 nullable로 둔다. 그래야 "아직 안 채운 것만
채우기"가 성립해 재실행이 안전하다. 클라이언트는 항상 숫자를 써넣는다.

## SQL을 아직 안 돌린 DB 대응

기존 코드에 환율 칸으로 같은 상황을 겪고 만들어둔 장치가 있다(`rateColsMissing` →
칸을 빼고 재시도). 같은 패턴을 `timelineColsMissing`으로 하나 더 둔다.

- 저장이 "칸 없음" 오류로 실패하면 해당 칸들을 빼고 **한 번 더 시도**한다.
  저장 자체는 절대 막지 않는다.
- 두 플래그가 동시에 걸릴 수 있으므로, 오류를 보고 플래그를 세운 뒤 재시도하는
  루프를 최대 2회 돈다.
- 이 상태에서는 타임라인 화면 상단에 `migration-timeline.sql 실행이 필요해요`
  안내를 띄운다.

## 화면

### 입력 화면 — "언제" 줄 추가

`낸 사람 / 나눠 갖는 사람` 줄 바로 위에 같은 모양의 줄을 하나 더 놓는다.

```
  ₩12,000
  [식비][카페][교통][숙소]
  내용 (선택)

  📅 3일차 · 🌆 저녁            바꾸기 ▾     ← 새로 추가
  민수가 냄 · 4명이 나눔        바꾸기 ▾

  [           저장           ]
```

기본값은 **지금 시각 기준으로 자동**이다. 현장에서 바로 넣을 땐 아무것도 안 눌러도
맞는다. 탭하면 패널이 열린다.

```
  며칠차
  [🎒 준비] [1일차] [2일차] [3일차] [4일차]

  언제
  [🌅 아침] [🍜 점심] [☀️ 오후] [🌆 저녁] [🌙 밤]
```

일차 칩은 `max(오늘 일차, 기록된 최대 일차)` + 1까지 보여준다(하루 미리 적을 수
있게). 시작일이 엉뚱하게 들어가 칩이 폭주하는 걸 막기 위해 상한을 60으로 둔다.

시작일이 아직 없는 방에서는 오늘 일차를 계산할 수 없으므로 기본값을 `1일차`로 둔다.

### 타임라인 화면 (`내역` 교체)

```
  ‹ 현황        타임라인

  [전체] [민수] [지현] [영훈]          ← 멤버 필터

  🎒 여행 전 준비                 ₩820,000
  ▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬
   ✈️  항공권          민수·4명   ₩640,000
   🛒  유심             지현·4명    ₩40,000

  1일차  8/1 (금)                 ₩318,500
  ▬▬▬▬▬▬▬▬▬▬▬
   🌅 아침
   │  🍚 편의점 삼각김밥  민수·4명   ₩4,500
   🍜 점심
   │  🍚 이치란 라멘      지현·4명   ¥1,200
   │                              ≈₩10,900
   🌆 저녁
   │  🍺 야키니쿠        민수·4명   ¥3,800
```

- 왼쪽에 세로 선(spine)을 긋고 시간대마다 점(이모지)을 찍는다. 빈 시간대는 아예
  그리지 않는다 — 안 쓴 시간을 빈칸으로 남기면 화면만 길어진다.
- 일차 헤더 아래 **가로 막대**가 그날 지출을 최대 지출일 대비 비율로 보여준다.
  "어느 날 크게 썼는지"가 스크롤 없이 읽힌다.
- 지출 행을 탭하면 기존 지출 모달이 열린다(수정·삭제·현장정산·환율).
- `day_index`가 비어 있는 행(마이그레이션 전)은 맨 아래 `❓ 미지정` 묶음으로 간다.

### 순서 조정 · 드래그 (2026-07-28 개정)

각 행 오른쪽 `⋮⋮` 손잡이를 잡아 **아무 시간대·아무 일차로** 끌어다 놓는다. 준비
구간도 대상이다. 처음엔 모달의 `↑위로/↓아래로` 버튼만 뒀는데(모바일 드래그가
스크롤과 충돌한다는 이유), 시간대를 잘못 넣은 걸 고치려면 결국 수정 화면을 거쳐야 해서
"바로바로 고친다"가 안 됐다. 버튼은 그대로 두되(드래그가 안 되는 상황의 대비책)
주 수단은 드래그다.

**스크롤 충돌은 손잡이를 따로 두는 것만으로 안 풀린다 (2026-07-28 실사용 사고).**
처음엔 손잡이에 `touch-action: none`을 걸었다. 그러면 거기서 시작된 터치는 **절대
스크롤이 안 된다.** 그런데 손잡이는 목록 오른쪽 끝, 폰에서 엄지가 스크롤하며 지나가는
바로 그 자리에 있다. 사용자가 목록을 넘기다 화면이 드래그 모드로 잠겨 아무것도 못 하는
상태가 됐다.

**`touch-action: pan-y` + `preventDefault`는 iOS에서 안 통한다.** 그 다음 시도가
이것이었다 — 손잡이를 `pan-y`로 두고 드래그가 걸리면 `touchmove`를 막는 방식. 데스크톱
크롬에선 완벽히 동작했고 iOS Safari에선 전혀 안 됐다. Safari는 `pan-y`가 허용돼 있으면
손가락이 움직이는 즉시 팬을 시작해버리고, **한 번 시작하면 `touchmove`가 cancelable이
아니게 되어 `preventDefault()`가 무시된다.** 팬이 시작되면 `pointercancel`이 날아오고
드래그는 그 자리에서 죽는다. 사용자 표현으로 "선택은 되는데 움직이면 살짝 스크롤되면서
풀린다".

지금 방식 — **브라우저에게 스크롤을 맡기지 않는다**:

- 손잡이는 `touch-action: none`. iOS가 이 터치로 팬을 시작할 여지를 아예 없앤다.
  드래그가 죽지 않는다.
- 그러면 손잡이 위에서 시작한 스와이프는 브라우저가 스크롤해주지 않으므로,
  **8px 넘게 움직인 순간부터 스크립트가 직접 `window.scrollBy`로 손가락을 따라간다.**
  오른쪽 끝이 스크롤 안 되는 죽은 띠가 되지 않는다. (관성은 없다.)
  이때 기준점은 손가락이 처음 닿은 지점이다 — 현재 위치로 잡으면 임계치까지의
  8px+가 통째로 버려져 스와이프가 늦게 붙는다.
- **터치는 320ms 가만히 눌러야** 드래그가 걸린다. 홀드 중에는 손잡이가 커지고 색이
  바뀌어 예고하고, 걸리는 순간 짧게 진동한다.
- **마우스는 즉시** 시작한다. 데스크톱엔 헷갈릴 여지가 없다.
- **포인터 캡처는 쓰지 않는다.** 캡처 대상이 손잡이인데 그 손잡이는 매 이동마다
  다시 붙이는 행 안에 있다. 캡처 중인 요소를 DOM에서 옮기면 캡처가 풀리며
  `pointercancel`이 나서 첫 움직임에 드래그가 죽었다. 이벤트는 `document`에서 받으므로
  캡처가 필요 없다. (합성 이벤트는 `setPointerCapture`가 거부해 예외가 나므로
  **브라우저 테스트에서는 이 버그가 절대 안 잡힌다** — 진짜 손가락에서만 난다.)
- `pointercancel`·`blur`·`visibilitychange`는 **"거기 놓기"가 아니라 "원래대로"**다.
  끊긴 제스처가 사용자가 고르지도 않은 자리에 지출을 박아넣으면 안 된다. 손가락을
  떼는 것만 저장이다.

구현에서 걸린 것들:

- **빈 시간대엔 놓을 수가 없다.** 평소 화면은 지출 있는 묶음만 그리므로, 드래그를
  시작하는 순간 `renderTimeline(true)`로 준비 + `0..오늘 일차` × 5시간대를 전부
  펼친다. 일차 수가 14를 넘으면(시작일이 엉뚱한 경우) 빈 일차는 만들지 않는다.
- **그 재렌더가 방금 누른 손잡이를 떼어낸다.** `ev.currentTarget`은 화면에서 사라진
  요소라 거기 리스너를 붙이면 손가락을 움직여도 아무 일도 안 일어난다. 재렌더 뒤
  새 행에서 손잡이를 다시 찾아 거기에 붙인다. jsdom 테스트가 같은 (떨어져 나간)
  요소에 이벤트를 쏘는 바람에 통과해버렸던 버그다 — 테스트도 살아있는 DOM에서
  손잡이를 다시 찾도록 고쳤다.
- **펼치면 내용이 밀린다.** 재렌더 직후 행의 위치 변화만큼 `scrollBy`로 되돌려
  손가락 아래에 그대로 있게 한다.
- **자리 잡기는 `pointermove`에서 직접 한다.** 프레임 루프(rAF)에만 맡기면 탭이
  백그라운드로 가거나 rAF가 throttle될 때 플레이스홀더가 멈춘다. rAF는 가장자리
  자동 스크롤 전용이다.
- **`⋮⋮`에 음수 자간을 주면 두 열이 겹친다.** 실제로 글자 폭 4px, 탭 영역 20px이
  나왔다. 자간 2px로 두어 34×41px을 확보한다.

저장은 **묶음 전체 재부여**다. `seq`를 맞바꾸는 대신 도착 묶음을 0,1,2…로 다시 매기고,
떠난 묶음도 빈틈을 메운다. 마이그레이션 전 데이터라 `seq`가 비어 있거나 겹쳐도 한 번
움직이면 정상화된다. 제자리에 놓으면 아무것도 쓰지 않는다.

### 멤버별 필터

- **진입 경로 2개**: 현황 화면의 잔액 행을 탭하거나, 타임라인 상단 칩을 탭한다.
- 멤버를 고르면 `[낸 것] [나눈 것]` 토글과 합계 줄이 뜬다.
  - **낸 것** — `payer_id`가 그 사람인 지출. 금액은 원래 금액 그대로.
  - **나눈 것** — `participant_ids`에 그 사람이 든 지출. 금액은 **그 사람 몫(원화)**,
    옆에 `(4인)` 표시.
- 몫 계산은 정산 계산(`computeSettlement`)과 **같은 규칙**을 쓴다 — 나누어떨어지지
  않는 나머지는 마지막 참여자가 흡수한다. 다른 규칙을 쓰면 필터 합계와 정산 금액이
  1~2원씩 어긋나 "왜 다르지"가 된다.
- 타임라인 구조(일차·시간대 묶음)는 필터를 걸어도 그대로 유지한다. 비는 날은 통째로
  숨긴다.

### 시작일 편집

현황 화면 상단에 한 줄 추가한다.

- 시작일이 있으면: `📅 여행 시작 8월 1일 (금)` + `바꾸기`
- 없으면: `📅 여행 시작일을 정해주세요` (경고색)

탭하면 날짜 입력 모달이 뜬다. 마이그레이션이 자동으로 채워넣긴 하지만 **첫날 지출이
없었으면 하루 밀렸을 수 있어서**, 사람이 한 번 확인할 자리가 필요하다.

## 안 하는 것

- **시간대 자동 추론(입력 시각의 hour로 판정)** — 마이그레이션에서만 쓴다. 새 지출에
  적용하면 이 기능을 만든 이유인 "뒤늦게 적는 경우"를 못 푼다.
- **일차별 예산/한도** — 정산 앱이지 가계부가 아니다.
- **지출의 실제 달력 날짜 저장** — `day_index`로 충분하고, `created_at`이 남는다.
